# Why the candidate masses come out below the sparticle mass. 2026-09-10.
# scripts/diagnose_candidate_mass.py reproduces every number here.
#
# SHORT ANSWER: the jet-to-candidate assignment is unbalanced, in the float
# PyTorch model. It is not quantization and not the hardware, and it is NOT
# confined to the second ABC layer.
#
# 1. WHAT THE MASS DEPENDS ON. get_jet_choice is an argmax over the first three
#    columns of x (with -1 on the ISR column). The mass uses the choice taken
#    AFTER THE LAST CROSS ATTENTION -- a different tensor from the per-layer
#    choices, which are taken after each OBJECT attention. That is why
#    stage4_final_jet_choice equals neither stage3_layer0_jet_choice nor
#    stage3_layer1_jet_choice.
#
# 2. THE ASSIGNMENT IS UNBALANCED EVERYWHERE (retrained_noncollapse, signal
#    gluino_rpv_6j, 2000 events, 8.7 real jets/event):
#      jet choice after   m_light  m_heavy  jets:c0  jets:c1  collapsed  light share
#      obj attention L0      259 G   2656 G     6.5      2.1        5%        24%
#      CROSS attention L0      0 G   3757 G     0.0      8.7      100%         0%
#      obj attention L1      327 G   2589 G     2.4      6.2        6%        27%
#      CROSS attention L1    484 G   2217 G     3.1      5.6        1%        34%   <- feeds the mass
#    Same pattern on QCD. So the claim that this happens only in the second ABC
#    layer is NOT supported: layer 0's own assignment is already 24% light. The
#    one total collapse is at the OUTPUT of layer 0's cross attention, which is
#    the INPUT to layer 1.
#
# 3. MECHANISM. The category scores carry a per-event common mode -- an offset
#    shared by every jet -- on top of per-jet variation. A jet can only differ
#    from its neighbours if the per-jet spread is comparable to the gap between
#    category means:
#      x taken after            gap(top-2 means)   per-jet spread   ratio   collapsed
#      obj attention L0                   0.207            0.525    0.39         1%
#      CROSS attention L0                 0.476            0.454    1.05       100%
#      obj attention L1                   0.034            0.286    0.12        15%
#      CROSS attention L1                 0.213            0.736    0.29         0%
#    Ratio above 1 means the common mode wins and every jet picks the same
#    category. Cross attention returns a mixture of only three candidate
#    vectors, so its output is nearly rank-2 across jets (event 0 singular
#    values 5.118, 0.359, 0.010, ...), which is why the common mode dominates
#    there.
#
# 4. SIZE OF THE EFFECT. For the same jets, the most balanced possible split
#    gives m_light 1657 GeV and m_heavy 1674 GeV -- consistent with the 1500 GeV
#    parent plus ISR. The model gives 484 and 2217. The light candidate is short
#    by about 1170 GeV purely because it receives 3.1 jets instead of 4.35.
#
# 5. NOT QUANTIZATION. Quantizing x to the deployed format (ap_fixed<16,7>,
#    truncating) flips 1 assignment in 13,912 jets (0.004%). The argmax margins
#    are median 1.88 against a quantization step of 0.00195, so the decision is
#    nowhere near the noise floor.
#
# 6. CHECKPOINT DEPENDENCE. The original 'replication' checkpoint is fully
#    collapsed: every jet lands in one category at every stage, and at the final
#    stage all of them go to ISR, so BOTH candidate masses are exactly zero.
#    'retrained_noncollapse' (the deployed one) mitigates this to the 3.1/5.6
#    split above but never balances it. The low masses are a training outcome.
#
# ===================== HOW TO FIX IT (tested, 2026-09-10) =====================
#
# A. INFERENCE-TIME CENTERING -- partial, free. Subtract each category's
#    per-event mean across jets before the argmax, removing the common mode:
#      sample              m_light      light share    AUC
#      gluino_rpv_6j       478 -> 703 G   34 -> 39%    0.9505 -> 0.9486
#      gluino_rpv_10j      694 -> 761 G   35 -> 37%    0.9699 -> 0.9714
#      squark_rpv_8j_2000  673 -> 842 G   33 -> 37%    0.9916 -> 0.9910
#    Recovers about a third of the imbalance at no cost in AUC. One line in
#    get_jet_choice; on hardware it is a mean over at most 12 jets per category,
#    cheap in both the fabric and the array. It does NOT reach a balanced split.
#
# B. FORCING A PHYSICALLY CORRECT MASS -- makes discrimination WORSE. Replacing
#    the mass feature with the most balanced two-way split of the same jets:
#      gluino_rpv_6j      AUC 0.9546 -> 0.8904
#      gluino_rpv_10j     AUC 0.9708 -> 0.9224
#      squark_rpv_8j_2000 AUC 0.9905 -> 0.9689
#    The autoencoder is trained on the mass distribution its own assignment
#    produces; a balanced mass is out of distribution for BOTH classes and
#    compresses the separation. So this is not a fix in any useful sense.
#
# C. RETRAINING is the only real fix, if physically meaningful candidate masses
#    are wanted. This is assignment collapse of the same kind as mixture-of-
#    experts routing collapse, and the usual remedies apply: an auxiliary
#    balance loss penalising deviation from an even split, a Sinkhorn or
#    optimal-transport assignment instead of a hard argmax, or Gumbel-softmax
#    with temperature annealing. The checkpoint name retrained_noncollapse says
#    this was already fought once; the 'replication' checkpoint is the fully
#    collapsed starting point.
#
# D. DOING NOTHING is defensible, provided the paper does not claim the
#    candidates reconstruct sparticle masses. They do not: the light candidate
#    is short by about 1170 GeV, and making it correct costs 0.02 to 0.06 AUC.
#    The mass is one of fourteen autoencoder input features and functions as a
#    learned summary statistic, not as a physical mass estimate.

################################################################################
# CORRECTION, 2026-09-11: THIS DIAGNOSIS WAS MEASURED ON A BROKEN MODEL
################################################################################
# Every number above was produced by a probe that NEUTRALISED the embedding's
# input BatchNorm (zeroing running_mean, setting running_var, gamma and beta to
# the identity) instead of fusing it into the first linear. That is the model
# with its input normalisation deleted, the same bug found the same day in
# scripts/make_auc_eval_set.py. The exported hardware weights are BN-FUSED, so
# the board always ran the full model; only this analysis did not.
#
# The deployed checkpoint, BatchNorm active, on gluino_rpv_6j:
#
#                         share   jets      m_light   m_heavy
#   as reported above      34%    3.2/5.9     605 G    2404 G
#   the real model         43%    4.2/4.9     993 G    1914 G
#
# THE HEADLINE CLAIM IS WRONG. The split is NOT badly unbalanced by jet count:
# 4.22 against 4.85 jets is a ratio of 1.15. But the masses still differ by
# 1.93x, and the reason is visible once the right quantity is measured:
#
#   lighter candidate   4.22 jets   sum pT 1041 GeV   mass  993 GeV
#   heavier candidate   4.85 jets   sum pT 1905 GeV   mass 1914 GeV
#   ratios              jets 1.15   sum pT 1.83       mass 1.93
#
# The mass asymmetry tracks ENERGY (1.83), not jet count (1.15). The model
# divides the jets nearly evenly by number and very unevenly by momentum: the
# hard jets go to one candidate and the soft ones to the other.
#
# That reframes the failure of the balance objectives in
# figs/balance_loss_negative_result.txt. They penalised COUNT imbalance. Even
# perfect count balance moves 4.22/4.85 to 4.5/4.5, a 7% correction, against an
# 83% energy imbalance. They were optimising the wrong quantity. (The
# train/eval mismatch recorded there is real and also applies; the share
# figures in that file are likewise ~9 points low for this same reason, though
# its relative comparisons and its training-log evidence stand, since those
# metrics came from the model itself during training.)
#
# AND THE ISR SLOT IS DEAD: 0.00 jets of 9.07. Only about six of those jets are
# signal, three per 1500 GeV gluino; the rest are ISR and are absorbed into the
# candidates instead of being set aside. The cause is a training hyperparameter,
# not the architecture: the deployed checkpoint was trained by retrain_tune.py
# with ISR=0.5, ten times the config's own scale_ISR_loss=0.05. That term
# charges the ISR candidate its full transverse energy, so emptying the slot is
# the cheapest solution available to the optimiser.
#
# Whether restoring the slot also fixes the energy skew, and at what cost in
# AUC, is measured in figs/isr_slot_sweep.txt. No candidate-mass quantity is
# used as a training target anywhere: forcing the two masses equal would build
# the signal's symmetry into a model that only ever sees QCD.
